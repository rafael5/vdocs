# 2026-08-01 — The pipeline audit, and P1: a corpus that had been quietly six documents short

*Session scope: `~/projects/vdocs`. Model: Fable 5 (audit + planning), Opus 5 (implementation).
Landed: `78ad07d` (audit) → `a3d2eee` (P1 close). Phases P2–P4 were executed by later sessions
and are not this session's work.*

## What was asked

An end-to-end adversarial analysis of the vdocs pipeline, with one framing constraint that
turned out to matter more than anything else in the request: **read the logic that actually
executes, not the documentation or the proposed work.** Four uses were named for it — human
audit, a reference for re-implementing in Go, traceability as the VDL source drifts, and a
method for building an accurate MCP service over the corpus.

## The audit

I read all 15 wired stages plus the serving layer, and cross-checked every claim against the
live lake (`~/data/vdocs`) rather than trusting any stage's self-report. The output
(`docs/reference/pipeline-adversarial-audit.md`) is a master table with one row per stage —
logic as coded, measurable input, the computable artifact the *next* stage reads, the coded
measure of "done and accurate", and a credibility grade — plus per-stage footnotes, an artifact
ledger, Go-port notes separating normative logic from incidental Python behaviour, the MCP
method, and a 16-row risk register.

The method that produced the findings was a single repeated question: not "what does this stage
do" but **"what failure would this stage's measure of done fail to see?"** That is what surfaced
the systemic finding. Every seam in the pipeline self-reports — `fetch` counts what it
downloaded, `convert` counts what it converted, `doctor` inspects only `index.db` — and
*nothing joined them*. A document could be recorded `fetched`, be missing from the raw index,
have no bundle anywhere downstream, and raise a finding in no gate at all.

Then I checked whether that was theoretical. It was not: **1,040 fetched acquisitions, 1,034
index entries.** Six documents gone, silently, because `raw/index.json` was keyed by content
sha256 and any two documents with byte-identical DOCX collapsed into one entry, last writer
winning.

Findings worth remembering beyond that one: 27.2% of live sections (containers + hollow) are
unsearchable *by construction*, because a section is classified `container` purely structurally
— next heading is deeper — regardless of how much lead-in prose it carries, and in a reference
manual that lead-in is the API contract. `doctor`, the only gate that inspects `index.db`, is
invoked by `build` and by hand but never by `vdocs run`. `retention_pure.blocks_publish` is dead
code, called only by its own unit test, while 7 low-retention documents sit in gold. And cheap
SQLite fingerprints are row counts, so a content-only change can skip its consumers.

## The plan, and a structure that paid off

Rather than fix things ad hoc I wrote an implementation plan + tracker + a per-phase kickoff
prompt folder, with one rule that turned out to be the right call: **prompts are written one
phase ahead, at the previous phase's close**, so each bakes in the measured results of the phase
before it instead of guessing them. P2's prompt could therefore open with a real baseline table
(1,040 documents, 615 anchors, doctor GREEN, 7 low-retention) that did not exist when the plan
was written.

Ordering was enforcement-first: fix the measured data defect (P1), then make the strongest gate
actually run (P2), then the enforcement holes (P3), then the substrate (P4/P5), then the largest
behavioural change (P6) last so it re-runs under sound skip and lineage semantics.

## P1, and the thing the design document had been right about all along

P1.1 stopped *merging* a sha-keyed index and started **deriving** the whole mapping each run
from acquisitions ⋈ the gate-admitted targets, keyed by `doc_id`. Three coupled defects fell out
at once: duplicate content stopped collapsing, withdrawn documents finally left the index (so
`convert`'s stale-bundle pruning could fire outside `--fresh`), and dict-insertion-order
winner-picking disappeared.

While implementing it I found that `vdocs-design.md` §5.5 **already specified** the index as "a
derived projection of `acquisitions`, regenerated by fetch, not a second source of truth." The
sha-keyed merge was the code deviating from its own spec. That is the sharpest vindication of
the "read the executed code" constraint in the original request: no amount of documentation
review could have found this, because the documentation was correct.

I also found a defect the audit had missed: a lost index entry **could not self-heal** on
re-run, because `SKIP_PRESENT` returns *before* the index write. Merging made the damage
permanent until a `--fresh` rebuild.

P1.2 built the join — `chain_pure.reconcile_chain`, five doc_id sets
(`admitted ⊇ fetched == raw_index == converted == normalized`), six typed finding kinds, each
naming the document it lost. "The chain lost 6" is arithmetic; "the chain lost `PSJ:psj_5_0_tm`"
is actionable. Each set is read from a *different* source, so the check cannot be satisfied by
one producer agreeing with itself.

P1.3 refused non-DOCX payloads at the CAS door — a 2xx WAF page was previously stored as
`<sha>.docx` in a write-once store, permanently, surfacing much later as an isolated convert
error.

## Three things I got wrong

**The audit named the wrong six documents.** It listed `CPRS:cprsguitm_0_636`,
`PSJ:psj_5_{nurse,supr}_um`, `PSJ:psj_5_tm`, `PSN:psn_4_{um,tm}` — those are the *survivors* of
each duplicate pair. I had read the first element of each pair instead of computing the set
difference against the index. The real casualties were `CPRS:cprsguitm`,
`PSJ:psj_5_0_{nurse,supr}_um`, `PSJ:psj_5_0_tm`, `PSN:psn_4_{tm,um}_r`. The count, the
mechanism, and the impact were all right; only the identifiers were wrong — which is its own
lesson, because the whole point of naming rows instead of counts is that they can be acted on,
and that only holds if the naming is itself derived. Corrected in [S4], the tracker, and the P1
prompt.

**My group-count prediction was wrong.** The P1 kickoff predicted consolidate would go 615 →
~617 because I believed the PSN pair had distinct version-group stems. It stayed 615: all six
folded into existing groups, because `slug_stem` correctly strips `r0218`-style revision tokens
and I had mis-recalled the slug as a bare `_r` suffix. Behaviour right, prediction wrong.

**The acceptance run found a corruption bug that neither the audit nor 1,132 passing tests
had.** After the full cascade re-ran, `merge` died with
`DatabaseError: database disk image is malformed`, and `PRAGMA integrity_check` showed real
btree damage. Cause: `build_atomic` `os.replace`s a fresh database onto `index.db`, but its WAL
hardening swept only the *temp's* `-wal`/`-shm`. The **target's** stale journal survived the
swap, and the next WAL-mode connection replayed an unrelated database's pages into the new file.
It is a shared kernel primitive — `serve-inventory`, `index` and `relate` all rebuild through it
— so any of them could have produced a corrupt store on a lake whose previous connection did not
close cleanly. Fixed as an unplanned P1.4 with a test that reproduces the exact sequence, and
logged as register row R‑17 with an explicit note that it was found by *running* the pipeline,
not by reading it.

That is the durable lesson of the session, and it went into the P2 prompt so later phases would
inherit it: **the live acceptance run is not a formality.** No fixture reproduced a real lake's
WAL state. The corpus was the only thing that could.

## Where it ended

The chain is equal at **1,040 across all six seams** (fetched acquisitions · raw index ·
converted bundles · normalized bundles · `doc_meta_staged` · `documents`), where it had been
1,040 vs 1,034. All six recovered documents came back with **zero downloads** — the bytes had
been in the CAS the whole time, so the loss was purely a keying artifact. One of them
(`CPRS:cprsguitm`) is 1.2 MB of manual that simply had not been in the corpus. `integrity_check`
ok, `validate` GREEN with `chain_findings=0`, **doctor GOLD LIBRARY: GREEN** (19 pass, 0 fail).

Register rows R‑2, R‑3, R‑8 and R‑10 struck with their commit hashes; R‑17 added.

## Notes for whoever reads this next

- The red path for the chain gate is proven by **four permanent integration tests**, not a
  one-off scratch-lake demo — deliberately, because tests cannot rot and a manual demo can. A
  fixture gotcha is recorded in the tracker: seed a broken chain **before** blessing the
  upstream, or you trip the drift preflight (or the empty-tree input check) instead of the gate
  you are trying to exercise.
- I used `git add -A` on several commits. The house rule is to stage only files you touched, and
  it exists precisely for the situation that later appeared in this repo: **concurrent sessions**
  (P2–P4 landed from other sessions while this one was open). Nothing was swept in, but it was
  luck rather than discipline.
- The corrupt database was quarantined rather than deleted (`index.db.corrupt-20260801*`,
  ~301 MB) so the evidence survived; deleting it is blocked by the sandbox under `~/data`, so it
  needs an external terminal:
  `rm -f ~/data/vdocs/index.db.corrupt-20260801{,-wal,-shm}`.
